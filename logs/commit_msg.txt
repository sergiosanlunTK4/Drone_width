BUGS DE IMPLEMENTACION (corregidos, detectados solo al ejecutar):
  1. class IOdictionary -> dictionary en transportProperties y turbulenceProperties.
     SISTEMICO: los 128 casos. blockMesh y checkMesh no lo detectan porque no leen el fichero.
  2. Rutas a los .py mal calculadas (../../scripts desde cfd/cases/<caso>/ no existe).
  3. topoSet: `type cylinderToCell` -> es una FUENTE: `type cellSet ; source cylinderToCell`.
  4. topoSet: falta la entrada `action`; y el cilindro media 2 cm con celdas de 0.2 m, asi que
     la cellZone salia VACIA (cellLabels List<label> 0()) y fvOptions avisaba "No cells selected".
     Corregido: grosor = 1.5 * tamano de celda base.
  5. fvOptions: `options` era una LISTA y debe ser SUB-DICCIONARIO; faltaba `upstreamPoint`
     (obligatorio en 2412); y `Cp = 0` provoca "Cp and Ct must be greater than zero".
     Cp se deriva ahora de teoria de disco: Cp = Ct*(1-a), a = (1-sqrt(1-Ct))/2.

ESTADO TRAS LAS CORRECCIONES: blockMesh OK, checkMesh "Mesh OK" (skewness 5e-14), topoSet
escribe 4 cellZones, simpleFoam CONVERGE en 268 iteraciones, los 3 function objects escriben,

BUG CONCEPTUAL #6 (CONFIRMADO EXPERIMENTALMENTE, no resuelto):
  El perfil de downwash bajo el rotor da Uz ~ 1e-7: EL FLUJO ES HORIZONTAL, NO HAY DOWNWASH.
  El disco se aplica (el log lista los 4 actuationDiskSource) pero no deflecta el flujo.

  CAUSA: `actuationDiskSource` en su metodo Froude NO aplica un empuje prescrito: lo CALCULA a
  partir del flujo incidente axial:
        T = 2 rho A |Uo . n|^2 a (1-a),      a = 1 - Cp/Ct
  Con flujo PERPENDICULAR al disco, Uo.n ~ 0 => T ~ 0, por muy correctos que sean Cp, Ct,
  diskArea, las cellZone y el solver.

  PRUEBA DISCRIMINANTE (scripts/test_axial_source.sh, copia TEMPORAL, el caso real intacto;
  el caso de prueba se elimino despues para no contaminar el conteo):
      flujo horizontal (3.108 0 0)   ->  Uz ~ 1e-7     (nulo)
      flujo vertical   (0 0 -3.108)  ->  Uz = -0.289 m/s (downwash real)
  Con flujo axial aparece downwash; con flujo perpendicular no. Confirmado.

  POR QUE ES GRAVE: el caso fisico del proyecto es el PEOR posible para este modelo. En hover el
  flujo axial entrante es ~0 porque el disco GENERA el flujo, no lo recibe. actuationDiskSource
  esta pensado para turbinas/helices en avance (flujo incidente -> T calculado); nosotros
  necesitamos lo contrario (T prescrito -> flujo generado). La arquitectura C->B queda sin
  implementar: T_i deja de ser una entrada y pasa a ser una salida.

  NO ERA UN PROBLEMA DE MALLA. La hipotesis de resolucion insuficiente se descarto ANTES de
  gastar computo, con una sola ejecucion. Refinar habria dado una representacion mas fina de
  una fuerza nula.

  CONSECUENCIAS: CFD-0 NO se cierra (un caso que converge a fisica nula no valida nada); la
  suite de 128 casos NO se escala con esta formulacion; cualquier downwash o deposicion obtenido
  asi seria invalido.

  CORRECCION NECESARIA: fuente de momento explicita que imponga
      integral_{V_disk,i} f dV = T_i     (vectorial, del equilibrio del UAV)
  con independencia del flujo incidente. Requisitos: independiente de U (debe funcionar con
  U_axial = 0), direccional segun el eje del rotor, vectorial por disco, y verificable
  integrando la fuerza aplicada. `meanVelocityForce` NO sirve: aplica fuerza global sobre todo
  el dominio, no por disco.
